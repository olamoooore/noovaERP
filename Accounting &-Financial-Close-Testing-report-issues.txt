Example of End to End workflow testing
Understanding E2E vs. Module Testing
Your intern was doing module-level bug hunting — clicking into each section individually. True end-to-end testing follows the full business transaction lifecycle: a dollar that enters the system must be traceable all the way to the closing balance sheet. Every step feeds the next. If you skip the sequence, you are not doing E2E testing.

PART 2: AI Assistant — Financial Close E2E Workflow
The AI Financial Close module's job is to identify outstanding/unresolved transactions, flag anomalies, and guide the team to close the period cleanly. Testing must validate the AI actually does this.
Setup Preconditions for AI Close Testing
Before testing AI Close, deliberately seed the system with:
                                                   * At least 1 unreconciled bank transaction
                                                   * At least 1 unposted journal entry
                                                   * At least 1 unpaid customer invoice (overdue)
                                                   * At least 1 unpaid vendor bill (overdue)
                                                   * At least 1 mismatched intercompany transaction (if multi-entity)
                                                   * A close cycle created for the current period (e.g. April 2026)
These are the "outstanding transactions" the AI should find and surface.

                                                   * Strict Order of Operations: The system must enforce a linear setup path. It must block data imports until the functional currency, local tax rules, and Chart of Accounts structure are defined.
                                                   * Immutable Core Settings: Once the first live transaction is posted, the system logic must lock down the Base Currency and Fiscal Year start date, making them unchangeable without a complete system reset


2. Import Validation & Parsing Logic 
                                                   * Data Type Enforcement: Import scripts must validate all inputs at the staging level. For example, text strings in "Opening Balances" or alphanumeric characters in date fields must be rejected instantly.
                                                   * Sanitization: The system must automatically strip formatting artifacts (such as currency symbols or spaces) from numeric columns before processing.
3. Mapping Engine Logic
                                                   * Classification Matching: The mapping logic must force a 1:1 or many:1 relationship between legacy accounts and new system categories. It must reject mappings that break accounting definitions (e.g., mapping a legacy "Bank Account" to a "Revenue" category).
                                                   * Control Account Isolation: The system must prevent users from mapping general historical balances directly to sub-ledger control accounts (Accounts Receivable/Payable) without providing the corresponding customer or vendor itemized breakdowns.
4. Mathematical Validation (The Hard Gate)
                                                   * Zero-Variance Trial Balance: The system must apply an absolute mathematical check on imported opening balances: Total Debits - Total Credits = 0.
                                                   * The Migration Lock: If a variance exists, the system logic must prevent the onboarding wizard from finishing. It must block the data from writing to the live General Ledger table until the discrepancy is corrected or allocated to a temporary suspense account.
5. Ledger Initialization Logic
                                                   * The "Day Zero" Snapshot: Upon final confirmation, the logic must convert the approved staging data into a closed "Opening Balance" journal entry dated exactly one day prior to the system's operational start date.
                                                   * Historical Data Isolation: The system must timestamp these entries as "Opening Balances" so that future balance sheets can cleanly differentiate between migrated historical wealth and new operational performance.

1. Purpose of Financial Close
What Financial Close Means
Financial Close is the process where accounting personnel confirm that all transactions for a period are complete, accurate, reviewed, supported, and ready for reporting.
It is not just “closing a page” or “clicking a dashboard card.”
It includes:
Transactions posted
      ↓
Bank reconciliations completed
      ↓
AR / AP balances reviewed
      ↓
Accruals, depreciation, journals checked
      ↓
Exceptions and anomalies identified
      ↓
Supporting evidence attached
      ↓
Tasks assigned and completed
      ↓
Reviews and sign-offs performed
      ↓
Period marked ready to close
What the AI Assistant Should Do
The AI assistant should assist accounting personnel, not replace accounting control.
It should help identify:
AI Responsibility
	Example
	Missing supporting documents
	Invoice has no attachment
	Unusual transactions
	Large expense compared with prior period
	Unreconciled items
	Bank transactions not matched
	Incomplete tasks
	Assigned reviewer has not signed off
	Risk areas
	AP balance changed significantly

11. Severity Guide for Financial Close
Critical / P0
Use when issue can cause incorrect close, wrong financial reporting, or security breach.
Examples:
                                                   * Close allowed despite unresolved blockers.
                                                   * Critical AI findings ignored by readiness gate.
                                                   * User can access another entity’s close data.
                                                   * Evidence can be deleted after sign-off/freeze.
                                                   * Posted accounting entries can be altered through close module.
                                                   * Reconciliation truth is overridden by Financial Close module.
Major / P1
Use when core workflow is impaired but not directly corrupting accounting truth.
Examples:
                                                   * Tasks not generated from close cycle.
                                                   * AI findings not persisted.
                                                   * Readiness score not updating.
                                                   * Escalation not working.
                                                   * Sign-off audit missing.
                                                   * Review lifecycle broken.
Medium / P2
Use when workflow is inconvenient or partially broken.
Examples:
                                                   * Overdue filter missing.
                                                   * Dashboard card routes to generic page.
                                                   * Back navigation missing.
                                                   * Duplicate widget appears.
                                                   * Raw UUID shown instead of cycle name.
Minor / P3
Use for cosmetic issues.
Examples:
                                                   * Label wording.
                                                   * Minor spacing.
                                                   * Non-blocking UI inconsistency.

Readiness calculation source:
All in FinancialCloseReadinessService.php:
                                                   * generateSnapshot() (line 25) — the main calculation:
                                                   1. Counts total_accounts, reviewed_accounts (status in submitted/approved/locked), signed_off_accounts (in approved/locked)
                                                   2. Counts open AI findings (status = 'open') grouped by review
                                                   3. Counts open critical tasks (is_critical = true, not completed/cancelled)
                                                   4. Calls buildSectionBreakdown() which scores each account using STATUS_WEIGHTS: locked/approved = 100, submitted = 50, in_progress = 20
                                                   5. readiness_score = sum(weights) / total_accounts
                                                   6. Fires FinancialCloseReadinessSnapshotGenerated event
                                                   * getReadinessSummary() (line 96) — is_ready gate: readiness_score >= 100 AND open_blockers === 0 (advisory only, not close truth)
