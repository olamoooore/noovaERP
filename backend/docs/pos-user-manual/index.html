System Overview

What is the POS System?

The POS (Point of Sale) system is the retail transaction processing engine for NoovaERP. It handles:

  • Order creation and item management
  • Payment processing (cash, card, digital)
  • Inventory management and stock tracking
  • Loyalty points earning and redemption
  • Session management and cashier accountability
  • Void/refund processing with proper governance
  • Offline order queuing and sync
  • Comprehensive audit logging

Key Concepts

Terminal: A physical POS device (register, kiosk, mobile device) where transactions occur.

Session: A cashier's work period on a terminal. Sessions have opening and closing balances for cash reconciliation.

Order: A customer transaction containing items, discounts, and payment information.

Payment: The method and amount used to settle an order (cash, card, loyalty points, etc.).

Loyalty Points: Customer rewards earned on purchases and reversed on refunds.

ℹ️ Session Requirement: All orders must be created within an active session. Sessions are opened at the start of a cashier's shift and closed at the end.

Core Workflows

1. Daily Startup Workflow

  1. Cashier logs into POS system
  2. Selects terminal from available list
  3. Opens new session with opening balance (cash in drawer)
  4. System confirms session is active
  5. Cashier ready to process orders

2. Order Entry Workflow

  1. Cashier creates new order
  2. Scans barcode or searches for product
  3. System validates barcode and confirms product details
  4. Item added to order with quantity
  5. Repeat for additional items
  6. Apply customer (optional)
  7. Apply discount (if authorized)
  8. Order ready for payment

3. Payment Processing Workflow

  1. Cashier initiates payment
  2. Selects payment method (cash, card, etc.)
  3. Enters amount received
  4. System processes payment through canonical completion service
  5. Payment is idempotent (duplicate requests produce no duplicate effect)
  6. Loyalty points earned (if applicable)
  7. Inventory deducted
  8. GL posting created
  9. Receipt generated
  10. Order marked as paid

4. Void Workflow (Target State)

  1. Cashier selects paid order to void
  2. Enters void reason
  3. System routes void through Sales module (canonical owner)
  4. Supervisor/Manager approval required
  5. Upon approval:
  6. ✓ Inventory reversed
  7. ✓ Loyalty points reversed
  8. ✓ GL reversal entry created
  9. ✓ Audit log recorded
  10. Order marked as void
  11. Refund payment recorded

5. Refund Workflow (Target State)

  1. Cashier selects paid order to refund
  2. Selects items to refund (partial or full)
  3. Enters refund reason
  4. System routes refund through Sales module (canonical owner)
  5. Supervisor/Manager approval required
  6. Upon approval:
  7. ✓ Inventory reversed for refunded items
  8. ✓ Loyalty points reversed proportionally
  9. ✓ GL reversal entry created
  10. ✓ Audit log recorded
  11. Return order created
  12. Refund payment recorded

6. Offline Order Workflow (Target State)

  1. Network connection lost
  2. Cashier continues creating orders (orders queued locally)
  3. Payment processing queued for sync
  4. Network restored
  5. System automatically syncs queued orders
  6. Sync is idempotent (duplicate orders prevented)
  7. All side effects applied (inventory, loyalty, GL)

7. Session Close Workflow

  1. Cashier counts cash in drawer
  2. Enters closing balance
  3. System calculates expected balance from session transactions
  4. Variance calculated and recorded
  5. Session closed
  6. Report generated for reconciliation

Critical Fixes in Target State

CRITICAL-001: Loyalty Points Reversal

Current Issue: Loyalty points earned on payment are not reversed when order is voided or refunded.

Target State Fix:

  • Event listener added for void/refund events
  • PointsEarningService::reversePoints() called on void
  • RedemptionService::reverseRedemption() called for redeemed points
  • Loyalty balance correctly reflects all transactions
  • Audit trail shows point reversal

CRITICAL-002: Offline Sync Mechanism

Current Issue: POS cannot operate offline. No offline order queue infrastructure.

Target State Fix:

  • PosOfflineOrder table created for queuing
  • Orders created during outage stored locally
  • Sync job replays offline orders when connection restored
  • Idempotency key prevents duplicate orders
  • All side effects applied on sync (inventory, loyalty, GL)
  • Cashier can continue working during network outage

CRITICAL-003: Session Enforcement

Current Issue: Payment can proceed without active session if session_id is null.

Target State Fix:

  • Session validation enforced on order creation
  • Session validation enforced on payment
  • Payment fails if session_id is null or session not open
  • Cashier identity always enforced
  • Terminal context always maintained

CRITICAL-004: Barcode Fallback Validation

Current Issue: Barcode resolution is deterministic but no validation before mutation.

Target State Fix:

  • Barcode resolution uses explicit ordering (deterministic)
  • Confirmation dialog shown for barcode fallback
  • Audit logging records barcode resolution method
  • Validation confirms barcode is correct before inventory mutation
  • Fallback to ambiguous fields prevented

CRITICAL-005: Entitlement Enforcement

Current Issue: Manager approval uses password check instead of entitlement system.

Target State Fix:

  • Manager role validated through entitlement system
  • Password-based approval replaced with entitlement check
  • Audit trail recorded through entitlement system
  • Void/refund approval enforced via EnsureEntitlementAccess middleware
  • No bypass paths for approval

WS-05 Sales Integration

Current Issue: Void/refund logic missing from Sales module. POS bypasses Sales entirely.

Target State Fix:

  • Sales module implements canonical refund/void/return lifecycle
  • POS void routes through SalesOrderService::void()
  • POS refund routes through SalesOrderService::refund()
  • All side effects cascade through Sales (inventory, loyalty, GL)
  • Unified refund trigger for all channels
  • Inventory reversal triggered on credit note posting

Important Notes

⚠️ Session Requirement: All orders must be created within an active session. You cannot process orders without opening a session first.
⚠️ Approval Requirements: Void and refund operations require supervisor or manager approval. These cannot be performed by cashiers alone.
ℹ️ Idempotency: All critical operations are idempotent. If a payment request is sent twice, only one payment is recorded. This prevents duplicate charges.
ℹ️ Offline Mode: The system can queue orders during network outages. When connection is restored, orders are automatically synced with no duplicate effect.
ℹ️ Audit Trail: All transactions, voids, refunds, and approvals are logged for compliance and reconciliation.
