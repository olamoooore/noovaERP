NoovaERP User Manual

Point of Sale Module

This manual is based on the current POS landing page, full-screen terminal, payment selector, settings tabs, barcode page, orders page, reports page, and offline queue. It corrects the earlier generic guidance and matches the current UI layout.

/pos and /pos/* Current Order left, Product Discovery right Documented only for exposed UI workflows

Scope

The current POS module covers terminal selection, session opening, selling through the full-screen terminal, barcode label generation, order review, reporting, offline sync monitoring, and POS settings.

The backend also supports returns, voids, refunds, held orders, and payment posting flows. This manual only describes workflows that are currently reachable through the existing frontend screens we inspected.

Most Important Correction

The live terminal layout is not a left-side product grid. In the current /pos/terminal screen, Product Discovery is on the right and Current Order is on the left.

POS Landing Page

The landing page at /pos is where operators choose a terminal and start or resume a register session.

What the Landing Page Shows

  • A grid of existing terminal cards
  • An Orders button that opens an order-review slide-over
  • A Barcodes shortcut to the barcode page
  • An Add New Terminal card for creating a new POS station

Terminal Card States

  • Active: the terminal matches the session store and is ready to resume.
  • Session in progress: the terminal has an open session and can be resumed.
  • Click to open session: the terminal has no open session and will launch the register-opening dialog.

Create or Edit Terminal

The current landing page create/edit dialogs capture:

  • Terminal name
  • Warehouse

Open Register

If a terminal does not already have an open session, clicking it opens the Open Register dialog.

Area Current behavior
Terminal and warehouse summary Shows the terminal name and warehouse selected for the session.
Staff assignment Requires choosing a staff member before the register can open.
Opening balance Accepts a direct amount entry and can also be auto-calculated from denomination counts.
Cash counting panel Optional calculator-like panel for notes and coins. It updates the opening balance automatically.
Notes Optional text entry for opening-cash comments.

How Sessions Open

When confirmed, the page posts to the session-open endpoint, stores the session in the POS session store, and then navigates to /pos/terminal.

Terminal Layout

The terminal runs inside the full-screen POS layout, not the normal sidebar layout. This is the live screen arrangement.

Left Side: Current Order

This column contains the draft order reference, customer selector, cart items, discount tools, totals, and the final PAY action.

Right Side: Product Discovery

This column contains search, manual barcode entry, category chips, warehouse and terminal badges, the product grid, and product pagination.

Product Discovery Panel

  • Header label: Product Discovery
  • Context badges: selected category, catalog item count, in-stock count, low-stock count, active warehouse, active terminal
  • Search input placeholder: Search products or scan barcode...
  • Category chips: All plus up to ten categories in the current chip row
  • Product cards show category badge, stock state, image, name, SKU, and price
  • Out-of-stock products are visually disabled

Barcode Entry Behavior

  • If the search box contains a numeric code of six or more digits and the user presses Enter, the terminal tries a POS product lookup.
  • The page also listens for very fast scanner-style keyboard bursts globally and turns them into barcode lookups.
  • If multiple barcode matches are returned, the current UI shows a message instead of opening a selection screen.

Current Order Panel

The left panel is the order workspace and is labeled Current Order.

Order Header Controls

  • Draft reference: shows the current order number or an in-progress draft reference.
  • Save Draft: stores the order as draft.
  • Clear Cart: clears items and resets discounts, loyalty redemptions, and draft identifiers.
  • View Pending Orders: opens the pending-order drawer and shows a badge if draft orders exist.

Customer Handling

  • The current order can stay as Walk-in.
  • The customer dialog lets the cashier search customers or open the Add New Customer dialog.
  • When a customer is selected, the panel shows phone number and loyalty details if the customer is enrolled.

Cart Items

  • Each line shows image, name, unit price, quantity controls, line total, and remove action.
  • The terminal blocks quantity increases above available stock.

Discount Tools

The live UI uses three tabs above the totals block:

Tab Current behavior
Discount Supports fixed-amount or percentage discount entry.
Loyalty Available only when a selected customer is enrolled and can redeem points under the returned loyalty rules.
Coupon Validates a coupon code through the POS coupon validation endpoint and applies the returned fixed or percent discount.

Totals Block

The totals area currently shows subtotal, tax, regular discount, coupon discount, loyalty discount, and final grand total.

Primary Checkout Action

The large bottom action is PAY, and it opens the payment selector dialog.

Payments

The terminal uses a payment selector component rather than hard-coded payment buttons.

How Payment Methods Are Shown

  • Methods are fetched dynamically from /pos-payments/methods.
  • They are grouped by category labels such as Cash Payment, Card Payments, and Bank Transfer / Offline.
  • Each method card shows its icon and name.

Reference-Based Methods

If a payment method requires a reference, the selector changes to a confirmation form showing:

  • Method name
  • Amount
  • Optional instructions from method config
  • Optional account details from method config
  • Reference number input

Online Gateways

  • If the selected method is configured as an online gateway, the terminal creates the order first and then routes into the appropriate payment dialog.
  • The current code explicitly supports HitPay and Stripe-style gateway dialogs when those methods are configured.

Do Not Assume Split Tender

The current terminal code and payment selector inspected here do not expose a cashier split-tender workflow. This manual therefore does not document split payments as a current operator feature.

Receipts and Labels

The current POS terminal supports receipt preview/download and direct printing when terminal IoT settings are configured.

Receipt Flow

  • The terminal builds a receipt object after successful payment.
  • If terminal settings are configured for direct receipt printing, the terminal attempts IoT receipt printing first.
  • If direct printing is not available or fails, the terminal falls back to a web print preview.
  • Receipt PDF download uses the order receipt endpoint.
  • Auto-print behavior depends on the POS runtime settings.

Barcode Labels

The barcode page at /pos/barcodes currently provides:

  • Product search by name, SKU, or barcode
  • Select-all and per-product selection
  • Quantity per product
  • Generate All and Print Selected actions
  • IoT label printing when a label printer is configured for the active terminal
  • Web print preview fallback when direct label printing is unavailable

Orders, Reports, and Offline Queue

Orders Page

  • Page title: Orders
  • Scope: both POS and Web orders
  • Stats cards: Total Orders, POS Orders, Web Orders, Total Revenue
  • Filters: search, source, status, and date
  • Order details load on demand when a record is opened

Reports Page

  • Summary cards: Today's Sales, This Month, Period Total, Average Order
  • Report type toggle: Daily or Monthly
  • Date filters: start date, end date, quick last-30-days, quick last-90-days
  • Main content: sales trend chart, detailed breakdown table, recent orders table

Offline Queue

  • Stats cards: Total, Pending, Synced, Failed, Conflicts
  • Auto-refresh toggle
  • Refresh and Sync All controls
  • Per-item status badges for pending, syncing, synced, failed, and conflict
  • Per-item retry and conflict resolution actions

POS Settings

The current settings page has five tabs: General, Terminals, Payment Methods, Receipt, and Barcode.

General

  • Order Number Prefix
  • Default Warehouse
  • Tax Mode
  • Rounding Method
  • Rounding Precision
  • Idle Timeout
  • Product listing and customer display settings, including Products Per Page, Default Product View, Enable Customer Display, and Customer Display Welcome Message

Terminals

  • Terminal Name
  • Warehouse
  • Receipt Print Mode
  • Receipt Header
  • Receipt Footer
  • Linked Agent
  • Receipt Printer (IoT)
  • Label / Barcode Printer (IoT)
  • Active / inactive state

Payment Methods

  • Name
  • Code
  • Type
  • Icon (Iconify name)
  • Surcharge percent
  • Surcharge fixed
  • Sort order

Receipt

  • Receipt Header
  • Receipt Footer
  • Logo URL
  • Paper Size
  • Receipt visibility toggles defined in the settings shape, including logo, tax breakdown, cashier display, and auto-print behavior

Barcode

  • Barcode Type
  • Render Format
  • Bar Width
  • Bar Height
  • Barcode label display flags defined in the settings shape, including price, name, and SKU visibility

Customer Display

The settings model also includes customer-display controls, and dedicated customer-display routes exist. Use them only when the display feature is enabled for the terminal environment.

Current Limits and Safe Notes

Returns, Refunds, and Voids

The backend exposes POS return, refund, and void endpoints, but the current cashier-facing pages inspected for this manual are centered on selling, order viewing, settings, reporting, and queue handling. This manual does not present a fake refund workflow that is not visibly wired into the current operator screens.

Session Close Exists

The current POS layout includes a close-session workflow with expected-versus-counted payment totals and optional cash denomination counting. Operators should use the built-in close-session flow rather than closing outside the module.

Backend Business Rule That Matters

On successful POS payment completion, the current backend is designed to keep stock deduction and GL posting together in one transaction boundary. This matters because payment completion is not only a cashier event; it is also a stock and accounting event.
